# Complete CDF CMOS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Teach the complete CMOS shipment, hazardous TCN, air manifest, printing, and release process described in the user's guides.

**Architecture:** Add a CDF CMOS workspace backed by pure shipment, hazardous-record, and manifest transitions. Store deployment manifest state separately from piece exercises, and adapt committed records to existing MSL, load planning, JI, grading, and departure consumers. Reuse the configurable Outbound shell while preserving its current defaults.

**Tech Stack:** Existing React, JavaScript, CSS, Jest, React Testing Library, and react-scripts; no new runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-10-13-cdf-cmos-design.md`

## Global Constraints

- Branding remains Transit IQ / 2T0X1 Training Portal.
- This remains a local simulation with fictional exercise data.
- The existing 30-minute release window remains an explicitly labeled training rule; neither PDF establishes it.
- No regulatory reference-data expansion is included.
- Preserve unrelated uncommitted workspace changes.
- No live CMOS connections, deployment, repository rename, or changes to Outbound workflow.
- Shared-shell changes must retain Outbound regression coverage.
- New full Guided/Test sessions begin without a created manifest or automatically completed CMOS tasks.
- Finished tests lock every mutation, including CMOS dialogs.

## Review Focus

- An imported session with duplicate or dangling assignment references must be rejected without replacing the active session (Task 4).
- Switching cargo selection while a dialog has unsaved edits must not save those edits to another TCN (Task 5).
- Multiple DG2 records for one piece must remain distinct when one record is edited or deleted (Tasks 2 and 5).
- Changed cargo after printing must not release using stale totals, checks, or documents (Tasks 3 and 7).
- Shared shell navigation changes must not expose CDF-only actions in Outbound or break its existing pages (Task 5).

## File structure and shared contracts

Create `src/Components/CdfCmos/` for this feature:

- `trainingData.js`: fictional mission, template, hazard, and ammunition expectations; `trainingData.test.js`.
- `shipmentLogic.js`: save and validate shipment/hazard records; `shipmentLogic.test.js`.
- `manifestLogic.js`: manifest creation, assignment, revisions, edit checks, print acknowledgments; `manifestLogic.test.js`.
- `CdfCmosWorkspace.js`: page navigation and dialog coordination; `CdfCmosWorkspace.test.js`.
- `ShipmentPlanning.js`: search/results and shipment record editor.
- `HazardousTcnDialog.js`: DG2 header and detail tabs; `HazardTemplateLookup.js` and `AmmoLotDialog.js`: focused lookup/lot dialogs.
- `AirManifest.js`: manifest search/results and editor; `ManifestAssignments.js`: searchable pallet/loose assignment dialog.
- `ReleaseAirShipment.js`: release dialog shared by Manifest and Departure entry points.
- `CargoPullSheet.js`: printable cargo pull document; `cdf-cmos.css`: screenshot-derived layout.

Use plain serializable objects:

- `ShipmentRecord`: existing `manifestFields` keys plus `t9Required`, `t9Remarks`, `hazardRecords`, `palletId` and stable `revision`.
- `HazardRecord`: `id`, `piece`, `templateId`, `templateType`, `certifier`, `page1`, `page2`, `hazardCode`, `lots`, `certificationStatement`.
- `LotRecord`: `id` and screenshot's lot number, DODIC, round count, NEW, UOM, pieces, weight, cube.
- `CdfCmosState`: `headerDraft`, `manifest` (null or saved header), `assignments`, `revision`, `checkedRevision`, `pullSheetRevision`, `manifestPrintRevision`, `releaseDetails`, `mistakes`, `feedback`.
- `Assignment`: `kind` (`pallet` or `loose`), `id`, and `pieceKeys`; a piece occurs in at most one assignment.
- `TransitionResult`: `{ ok, state, errors }`; errors use `{ field, message }`. Failed transitions retain valid committed data and entered drafts. Domain transitions receive time/IDs explicitly; do not read the clock or random generator internally.
- `Context`: `{ shipments, exercises, pieceKeys, destination, loadPlan, departure, departureAt, now, finished }`.

For every task below, run tests with `CI=true npm test -- --watch=false --runInBand --runTestsByPath <listed test files>`. A passing step means zero failed suites/tests and exit code 0. Before each commit, review and stage only that task's changes; preserve pre-existing edits in shared files by staging feature hunks. Do not commit unrelated workspace work.
